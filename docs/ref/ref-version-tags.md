# 版本 tag 历史记录

> 约定本身只写在 `AGENTS.md`（「版本号方案」/「tag 约定」/「升级版本号」）。本文只存历史证据：tag ↔ commit 映射、补打方法、异常判断。

## 背景

- 旧机制：versionName 的 patch 位是 build 计数，每次成功 build 自增；tag 只按 `X.Y` 里程碑打两段式（`v0.1` … `v0.8`，共 8 个，落在各 `X.Y.0` 的 bump commit 上）。
- 新机制（2026-10-11 起）：versionName 只手动升级（`scripts/build.sh --set-version A.B.C`），每次 build 只自增 versionCode；**任何 versionName 升级都打三段式 tag `vA.B.C`**。
- 本次按新约定回填：两段式 tag 全部改写为三段式，并补齐历史上每个 versionName。

## 补打方法（可复现）

扫描顺序用拓扑序，保证父提交先于子提交：

```bash
git rev-list --reverse --topo-order main -- pubspec.yaml
```

规则：

1. 取每个 commit 的 `version:` 值，`+` 之前的 `A.B.C` 为 versionName。
2. 每个 versionName 只在**首次出现**的 commit 打 tag。
3. 跳过 `1.0.0`（`flutter create` 模板默认值，方案未生效）。
4. 改写已有两段式 tag 时**保留原目标 commit**，只改名字。

结果：76 个轻量（lightweight）tag，`v0.1.0` … `v0.10.0`；本地与 origin 一致。

校验：逐个比对 tag 目标 commit 的 versionName 与 tag 名，76/76 一致。
